# Spark-Compatible Trusted Scoring — Design and Release Gates

**Status:** Proposed implementation plan; not deployed  
**Scope:** Replace browser-authoritative exam scoring with a trusted external endpoint while retaining Firebase Spark for the existing app.  
**Safety:** This document does not change Firebase billing, production Firestore rules, hosting, or student exam flows.

## Decision

Keep the Firebase Spark constraint as the default. Evaluate a separately hosted Cloudflare Worker as a candidate trusted scoring service. Do not assume the free tier is suitable for peak traffic until load-tested. If the free tier cannot meet the measured traffic and latency target, stop and present options; do not silently enable paid billing.

Cloudflare Workers Free currently documents 100,000 requests/day, 10 ms CPU time per invocation, and 50 external subrequests per invocation. These are platform limits, not a capacity guarantee for this app. A scoring request must be bounded and should avoid per-question network round trips.

## Security boundary

The browser is untrusted. Never accept a client-provided score, correct count, correct answers, answer explanations, or a trusted role flag as authoritative.

The scoring service must:
1. Require HTTPS and a Firebase Authentication ID token in the Authorization Bearer header.
2. Verify the token's signature and claims (aud, iss, exp, iat, non-empty sub) against the exact Firebase project ID. Cache Google signing certificates according to response cache headers and support key rotation. Reject malformed tokens and fail closed if verification cannot be completed.
3. Authorize the user to take the requested test. Authentication alone is not proof of purchase, enrollment, attempt ownership, or test eligibility.
4. Load the test definition and canonical answer keys only on the trusted service side. Do not trust question IDs or test configuration supplied by the browser without validating them against the published test definition.
5. Validate answer payload size, allowed response types, question membership, duplicate IDs, and time bounds.
6. Compute score server-side using the official marks and negative-marking policy from the trusted test definition.
7. Persist attempts with a server-generated attempt ID and authenticated UID. Enforce idempotency so retries do not create duplicate attempts or alter a previously finalized score.
8. Return only the score/result fields allowed by the product policy. Keep answer keys and explanations withheld until the configured solution-release condition is met.
9. Rate-limit by UID and other appropriate signals; add request IDs, structured redacted logs, and abuse monitoring. Never log ID tokens or answer keys.
10. Store all privileged credentials as the hosting provider's encrypted secrets. Never commit service-account private keys or put them in frontend environment variables.

Firebase documents that custom backends must verify Firebase ID tokens and validate the signature and claims; decoding a JWT without signature verification is not sufficient.

## Proposed endpoint contracts

### POST /v1/attempts:submit

Request:
- testId: required string, validated against a published test.
- responses: bounded map of question ID to the accepted response representation.
- clientAttemptId: optional idempotency key generated by the client; treated as untrusted and scoped to authenticated UID.
- timeTakenSeconds: telemetry only; validate bounds and never use it to prove eligibility.

Do not accept score, correctCount, incorrectCount, correctOption, answerKey, or explanations as authoritative request fields.

Success response (illustrative; final schema must match current UI contracts):
- attemptId
- testId
- score, correctCount, incorrectCount, unattemptedCount
- timeTakenSeconds
- solutionsAvailableAt or an explicit release state
- optional per-question review fields only if the solution policy allows them now.

### GET /v1/attempts/:attemptId/review

- Requires a valid Firebase ID token.
- Enforces ownership or explicit admin permission.
- Enforces solution-release policy on the server.
- Returns only review fields the user is currently allowed to see.
- Never exposes unreleased answer keys by merely guessing an attempt ID.

### GET /healthz

- Returns only a minimal health status; no project IDs, credentials, database contents, or internal configuration.

## Firestore access and least privilege

Before implementation, choose a credential/access model. A service account that can read all production data is a high-impact secret. Prefer a dedicated service identity and narrowly scoped data model/permissions where feasible. Verify exactly which Firestore IAM permissions are required and whether they can be restricted sufficiently for the selected REST access pattern. Do not create a broad service-account key until the permission design is reviewed.

If the worker uses Firebase ID token verification, it must check the exact project audience and issuer and validate the RSA signature using Google's published certificates. It must handle certificate rotation and fail closed on verification errors.

## Migration plan — do not skip gates

1. Freeze the current public behavior and record current UI request/response contracts.
2. Add pure, deterministic scoring tests for all question types and negative marking; include malformed/oversized input, unknown questions, duplicate submissions, and boundary values.
3. Implement the worker as an isolated package with no production credentials. Add local unit tests for authentication rejection, authorization, payload validation, scoring, idempotency, and solution-release policy.
4. Test against a dedicated non-production Firebase project and synthetic accounts only. Never use live student data for initial integration tests.
5. Migrate the browser to submit answers to the trusted endpoint. Keep current student read paths working during the transition; do not switch to projection-only question data until exam delivery, scoring, review, and offline behavior are migrated.
6. Validate response contracts against ExamEngine, examScoring, SolutionsScreen, attempt persistence, PYP, and offline flows.
7. Backfill studentQuestions in bounded batches against the intended environment, then run the full verifier and reconcile all differences.
8. Run end-to-end tests: eligible/ineligible user, anonymous user, cross-user attempt access, unreleased/released solutions, repeated submission, network retry, interrupted attempt, admin review, and offline behavior.
9. Run staged load tests with realistic test lengths and concurrency, starting low and increasing gradually. Record p50/p95/p99, error rate, Firestore reads/writes, Worker CPU, rate-limit behavior, and daily request budget. Do not jump directly to a 2,500-VU production test.
10. Only after all gates pass, schedule a controlled rollout with monitoring and a rollback path.
11. Tighten Firestore rules to deny student reads of canonical answer-key documents only after every legitimate student/admin/public solved-question access path is accounted for and verified in tests.

## Rollback

Keep the existing deployment and rules unchanged during development. A rollback must be able to disable the new client endpoint path without exposing canonical answer keys publicly. Do not use rollback as a reason to reopen public canonical reads after answer-key confidentiality is promised.

## Blocking decisions / release checklist

- [ ] Confirm the exact Firebase project ID and environment used for non-production testing.
- [ ] Map official marks, negative marking, multi-correct/matching questions, partial credit, cancelled questions, and solution-release policy to current implementation.
- [ ] Determine attempt ownership, purchase/enrollment checks, and admin authorization rules.
- [ ] Review least-privilege Firestore IAM and secret rotation plan.
- [ ] Build isolated worker package and automated tests.
- [ ] Pass non-production end-to-end tests.
- [ ] Pass staged load tests against agreed targets.
- [ ] Complete full student read-path migration.
- [ ] Run projection backfill and verifier with an explicit operator window.
- [ ] Review and test final Firestore rules before rollout.
- [ ] Owner approval before production rules changes, merge, deployment, or any billing change.
