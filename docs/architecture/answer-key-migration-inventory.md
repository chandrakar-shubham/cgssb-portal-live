## Required separation of data contracts

1. **Canonical/admin question** — answer key, explanations, moderation/internal fields; readable only by authorized admin/service.
2. **Student delivery question** — question content and options only; no correct answer, explanation, hidden metadata, or answer marker in nested objects.
3. **Accepted attempt result** — score and counts generated by the trusted backend, tied to the authenticated UID, immutable/idempotent submission ID and server-selected test definition.
4. **Solution review payload** — answer key and explanation returned only according to the test's release policy; public SEO publication is a separate explicit content decision.

## Verification plan before rules change

- Add tests that scan every client-side student entry point for canonical reads and assert student components consume the safe DTO type.
- Test a non-admin user cannot read canonical question docs or write projections.
- Test an altered client score is ignored; duplicate submission IDs return the same accepted result; cross-user attempt writes fail.
- Test unreleased solution requests are denied and intentionally published SEO questions still render correctly.
- Test start/resume/offline-cache/submit/retry/review/reattempt end-to-end.
- Run the projection backfill and verifier only against an explicitly selected production project after operator confirmation; record canonical/projected counts, full coverage, mismatches, leaks, and timestamp.
- Run load tests against the trusted endpoint and agree on error-rate/latency SLOs before launch.

This is a source-code audit of the stated branch, not a live Firestore audit. It does not establish the current production document counts, projection completeness, deployed rules, or production deployment SHA. Those require separate verified checks.
